# 클로드 전달용: 졸업논문 진행 관리 보드 프로젝트 설명 및 발표자료 제작 요청

기준일: 2026년 9월 22일. 아래 설명은 프로젝트의 최신 코드와 README를 확인하여 정리한 것입니다. 초기 기획과 현재 구현이 다른 부분은 현재 구현을 기준으로 작성했습니다.

## 1. 요청하는 결과물

이 문서를 바탕으로 프로젝트 심사용 발표자료를 PPTX 형식으로 제작해 주세요.

- 전체 분량은 5페이지입니다. 별도 표지를 만들지 말고, 첫 페이지에 프로젝트 제목을 크게 배치한 뒤 바로 내용을 설명해 주세요.
- 발표자가 구두로 보충하는 발표용 슬라이드가 아니라, **심사위원이 자료만 읽고 프로젝트의 배경·문제·해결 방식을 이해하는 독립적인 심사자료**입니다.
- 컨설팅 보고서처럼 각 페이지의 핵심 주장과 이를 뒷받침하는 구체적인 설명·사례를 연결해 주세요. 짧은 슬로건이나 추상적인 키워드만 나열하지 마세요.
- 기능을 설명하기 전에 문제 선정 이유, 학과별 절차의 차이, 다전공생의 정보 탐색 부담을 충분히 설명해 주세요.
- 기본 구성은 배경 3페이지, 기능·해결 방식 2페이지입니다. 각 페이지 안에서 정보의 우선순위를 정하고 상세 기능은 핵심 흐름을 이해하는 데 필요한 것부터 선택해 주세요.
- 한국어를 사용하고, 핵심 설명을 발표자 노트에만 넣지 마세요. 본문만 읽어도 논리가 완결되어야 합니다.
- 관찰에 기반한 문제 인식, 공식 공지로 확인한 사실, 현재 구현된 기능, 향후 과제를 구분해 주세요.
- 실제 조사하지 않은 다전공 비율, 사용자 수, 시간 절감률, 만족도 등을 만들지 마세요. 기대 효과는 목표나 가설로 표현해 주세요.
- 프로젝트는 서울대학교 학생의 경험을 출발점으로 하지만, 학교의 공식 서비스나 공식 도입 사업은 아닙니다.

## 2. 프로젝트 한 문장 정의

**학과별로 다른 졸업논문 절차를 학생의 전공에 맞는 로드맵으로 제공하고, 학생의 신청·제출과 교수의 검토, 학과 조교의 절차·공지 관리를 연결하는 웹앱입니다.**

주요 사용자는 주전공과 복수전공의 졸업논문 절차를 함께 관리해야 하는 학생입니다. 학생뿐 아니라 교수와 학과 조교가 각자의 화면에서 같은 진행 정보를 확인하고 처리합니다.

서비스가 다루는 핵심 질문은 다음과 같습니다.

> 내 전공에서 지금 무엇을 해야 하고, 언제까지 어디에 제출해야 하며, 누구의 확인을 기다리고 있는가?

졸업논문의 내용을 대신 작성하는 서비스가 아닙니다. 논문 작성 전후에 필요한 신청, 일정 확인, 제출, 검토, 보완 등의 절차를 관리하는 서비스입니다.

## 3. 기획 배경과 문제 정의

### 3.1 대학생이라는 신분을 문제 발견과 검증의 강점으로 활용

기획자는 대학생이라는 신분이 핸디캡이 아니라 상대적인 강점이 될 수 있는 문제를 고르고자 했습니다. 학생이 직접 겪는 문제라면 공지와 실제 행동 사이의 불편을 가까이에서 관찰할 수 있고, 전공 조합이 다른 동료 학생을 통해 필요한 정보를 확인하기도 쉽다고 판단했습니다.

이러한 기준으로 학부생의 졸업 준비 과정, 특히 졸업논문을 진행하기 위한 행정 절차에 주목했습니다. 모든 학부생은 졸업요건을 확인해야 하지만, 졸업논문 자체의 필수 여부와 대체 요건은 학과·전공 유형에 따라 다릅니다. 따라서 “모든 학부생이 반드시 졸업논문을 작성한다”라고 일반화하지는 않습니다.

주변 학생에게 접근하기 쉽다는 설명은 기획상의 이점입니다. 실제 인터뷰나 설문을 이미 수행했다는 뜻은 아닙니다.

### 3.2 핵심은 학과마다 절차가 다르다는 점

졸업논문이라는 이름이 같아도 시작 방법과 완료 조건은 다를 수 있습니다.

| 절차의 예 | 학생이 수행하는 일 | 별도로 확인해야 하는 정보 |
|---|---|---|
| 개별 연락·승인 중심 | 교수에게 연락하고, 연구계획이나 신청서를 제출하여 승인받은 뒤 논문을 작성 | 연락 시점, 신청 서식, 승인 여부, 후속 제출 기한 |
| 교과목 운영 중심 | 졸업 세미나나 관련 수업을 수강하고, 수업 안에서 지도·점검·과제를 진행 | 수강 과목과 분반, 지도교수 결정 방식, 수업별 제출 일정 |
| 논문·발표 병행 | 논문 작성·제출에 더해 발표회나 포스터 발표 및 심사를 진행 | 발표 의무, 발표 자료, 참석 일정, 최종본 제출 기준 |

이 유형들은 서로 배타적이지 않습니다. 예를 들어 수업을 통해 논문을 진행하면서 별도의 발표회에도 참석해야 할 수 있습니다. 한 학과에서 알게 된 경험을 다른 학과에 그대로 적용하기 어렵다는 것이 중요합니다.

### 3.3 다전공생은 서로 다른 절차를 동시에 관리

기획자는 서울대학교에서 다전공 이수가 매우 보편적이라고 느낀 경험을 문제의 출발점으로 삼았습니다. 다전공생에게는 주전공 학과의 절차를 아는 것만으로 충분하지 않으며, 복수전공 학과의 논문 요건과 신청·제출·발표 일정을 별도로 확인해야 합니다.

다전공생이 실제로 “대부분”이라는 공식 비율은 확인하지 않았습니다. 수치가 필요한 자료에서는 별도 근거가 필요합니다. 발표자료에서는 “서울대 다전공생의 경험에 주목했다”, “서로 다른 학과의 절차를 함께 관리해야 한다”라는 점을 중심으로 설명해 주세요.

### 3.4 공지 채널과 인적 연결의 차이가 정보 탐색 부담을 확대

기획자가 관찰한 상황은 다음과 같습니다.

1. 학과마다 메일, 학과 게시판 등 안내하는 방식과 위치가 다릅니다.
2. 학생은 여러 학과의 공지를 반복해서 검색하며 새 안내, 변경된 일정, 제출 서식을 찾아야 합니다.
3. 복수전공 학과에는 아는 동기나 선배가 없는 경우가 있어, 공지의 의미나 실제 진행 방법을 물어볼 사람이 부족합니다.
4. 학생 익명 커뮤니티에 질문하여 정보를 보완하지만, 답변이 최신 규정인지, 자신의 학번이나 전공 유형에도 적용되는지는 다시 확인해야 합니다.

익명 커뮤니티의 모든 정보가 부정확하다는 의미는 아닙니다. 개별 답변의 최신성·적용 범위·공식 근거를 검증하기 어렵다는 점이 문제입니다.

### 3.5 최종 문제 정의

**학과별 공식 정보가 분산되어 있고 적용되는 절차도 달라, 학생 개인이 정보를 수집하고 해석한 뒤 자신의 전공별 일정과 행동으로 다시 정리해야 합니다. 다전공생은 이 과정을 여러 학과에 대해 반복합니다.**

이로 인해 반복 탐색, 추가 문의, 제출처 혼동, 일정 변경 인지 지연이나 마감 누락의 위험이 발생할 수 있습니다. 이러한 영향의 발생률이나 소요 시간을 정량적으로 측정한 것은 아닙니다.

## 4. 해결 방식과 핵심 설계

### 4.1 학과별 차이를 유지하는 절차 데이터

학과마다 정해진 절차를 화면 코드에 고정하지 않고 데이터로 관리합니다. 학과의 단계 구성이 다르면 학생의 로드맵도 달라집니다.

학과 데이터에는 학과명, 적용 학기, 대상 졸업예정 학기, 주전공·복수전공별 필수/면제 요건, 지도교수 결정 방식, 출처 정보, 공식 링크, 단계 목록 등이 있습니다.

각 단계에는 다음 정보가 들어갑니다.

- 단계명과 설명, 시작일과 마감일
- 대상: 전체 / 주전공 / 복수전공
- 진행 방식: 신청, 교수 승인, 자료 검토, 수강 확인, 활동 완료 기록 등
- 제출물, 제출처, 관련 서식
- 필수 여부, 예외사항과 유의사항, 담당 연락처

학생이 여러 전공을 이수하더라도 진행 상태는 전공별로 구분합니다. 한 전공에서 승인을 받아도 다른 전공의 로드맵은 자동으로 완료되지 않습니다.

### 4.2 세 역할의 업무를 연결

| 역할 | 주된 책임 | 다른 역할과의 연결 |
|---|---|---|
| 학생 | 자신의 절차 확인, 지도 신청, 자료 제출, 면담 시간 선택 | 교수에게 신청·제출물을 보내고 검토 결과를 확인 |
| 교수 | 신청·제출물 검토, 피드백, 면담, 지도 정원 관리 | 학생에게 승인·수정 요청·면담 제안을 전달 |
| 학과 조교 | 학과 절차와 공지 게시, 소속 학생 진행 현황 확인 | 게시한 내용을 학생의 로드맵·공지·일정에 반영 |

최신 화면에서 행정 역할의 명칭은 **학과 조교**입니다. 필요하면 “학과 조교(행정 역할)”로 표기해 주세요.

## 5. 학생 화면의 상세 기능

### 5.1 전공별 현황과 업무 탐색

- 학생 이름, 학번, 졸업예정 학기, 초과학기 여부를 표시합니다. 시연 인물은 가상입니다.
- 주전공·복수전공별로 완료 단계 수와 현재 단계의 D-day를 요약합니다.
- 전공 탭으로 학과를 전환합니다. 전공 선택과 업무 선택은 별도로 제공합니다.
- 업무는 **로드맵 / 지도교수 / 면담 일정 / 연구계획·논문 / 캘린더 / 공지**의 6개 탭으로 구분합니다.
- 다음 할 일 버튼, 캘린더 일정, 알림을 누르면 관련 전공과 업무 화면으로 이동합니다.
- 탭 이동이나 새로고침 후에도 저장한 초안이 유지됩니다.

### 5.2 다음 할 일

- 선택한 전공의 현재 단계에 맞춰 다음 행동 하나를 강조합니다.
- 행동 이름, 마감일, D-day, 제출처와 설명, 실행 버튼을 제공합니다.
- 상황에 따라 교수 찾기, 면담 시간 선택, 연구계획 작성, 최종논문 제출, 수강 분반 선택 등으로 바뀝니다.
- 제출 후에는 교수 검토를 기다리는 상태를 보여줍니다.

**정확한 현재 동작:** 모든 전공에서 가장 급한 한 건을 자동 선정하는 방식이 아니라, **현재 선택한 전공의 다음 할 일**입니다.

### 5.3 전공별 세로 로드맵

- 학과 조교가 게시한 절차를 순서대로 표시합니다.
- 완료 / 진행 중 / 예정 / 마감 지남 / 보완 필요 등의 상태를 구분합니다.
- 각 단계에서 기간, 제출물과 제출처, 서식, 유의사항 등을 확인합니다.
- 수정된 일정은 게시 후 일정 변경 배지로 표시하며, 현재 구현의 표시 기간은 7일입니다.
- 데이터상 논문 면제 전공은 면제 안내를 표시하고, 요건이 누락된 경우에는 정보 확인 필요를 안내합니다.
- 발표 참석이나 외부 학과 제출 등 일부 활동은 학생이 수행 후 완료를 기록하는 데모 방식입니다. 실제 학사 확인을 자동 검증하는 기능은 아닙니다.

### 5.4 교수 탐색과 지도 신청

- 단과대학, 학과, 연구 분야, 키워드로 교수를 검색합니다.
- 교수의 소속, 연구 분야·키워드, 남은 자리와 연락처·연구실 링크 정보를 확인합니다.
- 현재 전공의 교수 중 신청 가능한 사람을 선택합니다.
- 연구 제목, 연구 방향 요약, 연구계획 본문 또는 PDF/DOCX, 면담 희망 여부를 작성합니다.
- 자동 저장과 수동 임시저장을 지원합니다.
- 정원이 찼거나 모집을 종료한 교수에게는 신청할 수 없으며 이유를 표시합니다.
- 신청 상태는 제출됨(검토 대기), 수정 요청, 면담 요청, 승인, 반려로 구분합니다.
- 제출 후 검토 중에는 신청서가 읽기 전용이 됩니다. 수정 요청을 받으면 기존 교수에게 보완하여 재제출할 수 있습니다.
- 반려된 경우 새로운 신청을 작성할 수 있습니다.

**현재는 서비스 안에서 보내는 신청이 교수에게 하는 첫 연락입니다. 사전에 별도로 연락했는지를 체크하는 절차는 없습니다.**

### 5.5 면담 일정 조율

- 교수가 제안한 여러 가능 시간을 확인합니다.
- 제안된 시간 중 하나를 선택하여 면담을 확정합니다.
- 확정 시 학생과 교수에게 앱 내 알림을 전달하고, 학생 캘린더에 반영합니다.
- 이미 확정된 면담과 동일한 시각에 겹치는 예약을 제한합니다.
- 면담 장소 또는 온라인 링크를 확인할 수 있습니다.

### 5.6 연구계획·중간점검·최종논문 제출

- 현재 단계가 제출 단계가 되면 제목, 본문, 파일을 작성·첨부할 수 있습니다.
- 연구계획서는 본문 또는 PDF/DOCX 파일로 제출할 수 있습니다.
- 최종논문은 PDF/DOCX 파일 첨부가 필수입니다.
- 중간점검처럼 교수의 확인이 필요한 자료도 제출·검토 흐름을 사용할 수 있습니다.
- 자동 저장과 임시저장을 지원하고, 제출 후에는 검토 상태를 확인합니다.
- 수정 요청을 받으면 피드백을 반영하여 재제출합니다.
- 재제출은 v1, v2와 같은 새 버전으로 쌓이며 이전 제출 기록이 남습니다.
- 교수 승인으로 해당 제출 단계가 완료되고 다음 단계로 진행합니다.

### 5.7 모든 전공을 합친 캘린더

- 모든 전공의 단계별 마감, 확정 면담, 일정이 있는 공지를 한곳에 모읍니다.
- 월간 달력과 기간을 보여주는 타임라인·간트 보기로 전환할 수 있습니다.
- 전공별 색상과 표시 필터로 일정을 구분합니다.
- 일정 클릭 시 해당 전공의 관련 단계·면담·공지로 이동합니다.

**현재는 학생이 일정을 함께 보고 겹침을 파악하는 기능입니다. 전공 간 같은 주의 마감 충돌을 자동 경고하는 기능은 현재 구현으로 설명하지 마세요.**

### 5.8 맞춤 공지

- 학생의 학과, 적용 학기, 주전공/복수전공 유형, 졸업예정 학기에 맞는 공지를 보여줍니다.
- 공지 본문과 첨부파일을 확인합니다.
- 공지에 날짜가 있으면 통합 캘린더에도 반영합니다.

## 6. 교수 화면의 상세 기능

### 6.1 지도 정원과 모집 상태

- 학년도, 총 지도 정원, 승인 인원, 검토 대기 인원, 남은 자리를 확인합니다.
- 정원과 모집 중/마감 상태를 수정할 수 있습니다.
- 정원을 현재 배정·승인 인원보다 작게 낮출 수 없습니다.
- 남은 자리가 없으면 새로운 신청을 승인할 수 없습니다.
- 같은 신청을 중복 승인하여 인원이 계속 늘어나는 것을 방지합니다.

### 6.2 지도 신청 검토

- 자신의 신청 목록을 상태별로 필터링합니다.
- 학생의 전공, 주전공/복수전공 구분, 졸업예정 학기, 신청일과 연구 제목·요약을 확인합니다.
- 상세 내용을 펼쳐 연구계획 본문과 첨부파일을 검토합니다.
- 승인 / 수정 요청 / 면담 요청 / 반려를 처리합니다.
- 수정 요청, 면담 요청, 반려에는 피드백 입력이 필수입니다.
- 승인하면 학생의 해당 전공 지도교수 단계가 즉시 완료되고, 진행 단계와 승인 인원이 갱신됩니다.

### 6.3 면담 시간 제안과 완료 기록

- 30분 단위 시간 그리드에서 미래의 가능 시간을 여러 개 선택합니다. 연속 구간 드래그 선택도 지원합니다.
- 장소나 온라인 링크를 함께 전달할 수 있습니다.
- 학생이 선택한 확정 시간을 확인하고, 면담 후 완료 처리합니다.

### 6.4 제출물 검토와 피드백 이력

- 연구계획서와 최종논문을 구분하여 확인합니다.
- 파일 또는 본문과 제출 버전을 검토하고 승인하거나 수정 요청을 보냅니다.
- 수정 요청에는 보완할 내용을 입력해야 합니다.
- 기존 피드백을 수정할 수 있으며 이전 내용과 수정 시각을 보관합니다.
- 학생에게 검토 결과 및 피드백 수정 알림을 전달합니다.
- 별도 탭에서 자신이 지도하는 학생 목록을 확인합니다.

## 7. 학과 조교 화면의 상세 기능

### 7.1 학과별 절차 편집기

- 적용 학기, 대상 졸업예정 학기, 지도교수 결정 방식을 설정합니다.
- 단계를 추가하거나 삭제하고, 드래그 또는 위·아래 버튼으로 순서를 바꿉니다.
- 단계명, 진행 방식, 대상 전공 유형, 시작일·마감일, 제출물·제출처, 설명, 예외사항, 연락처, 필수 여부와 첨부 서식을 편집합니다.
- 편집 결과가 학생에게 어떻게 보일지 로드맵 미리보기로 확인합니다.
- 자동 임시저장과 수동 임시저장을 지원합니다.
- 초안 편집 중에는 학생 화면이 바뀌지 않습니다. **게시해야** 학생의 로드맵과 일정에 반영됩니다.
- 게시 시 해당 학과 학생에게 앱 내 알림을 전달합니다.
- 한 학과의 활성 게시 절차 1개를 관리하며, 학기별 전체 아카이브를 운영하는 기능은 없습니다.

### 7.2 대상별 공지 작성

- 공지 제목과 본문, 적용 학기, 대상 졸업예정 학기를 입력합니다.
- 대상은 전체, 주전공, 복수전공으로 구분할 수 있습니다.
- 관련 절차 단계, 선택적 일정, 첨부파일을 지정합니다.
- 초안 저장과 게시를 구분합니다.
- 게시하면 조건에 해당하는 학생에게 공지와 알림을 전달합니다.

### 7.3 학과 학생 검색과 진행 조회

- 해당 학과를 주전공 또는 복수전공하는 학생을 조회합니다.
- 이름·학번, 졸업예정 학기, 주전공/복수전공, 현재 진행 단계로 필터링합니다.
- 초과학기 학생과 지연 학생을 따로 볼 수 있습니다.
- 학생별 지도교수, 현재 단계, 다음 마감과 로드맵 상세를 확인합니다.
- 학생 진행 조회는 읽기 전용입니다.

**학과 조교가 지도교수를 임의 배정하거나 교수 정원을 변경하는 기능은 없습니다. 교수 승인 뒤 조교가 다시 확정하는 단계도 없습니다.**

## 8. 지도교수 결정 방식과 핵심 동작 규칙

현재 시스템의 지도교수 결정 방식은 두 가지입니다.

| 구분 | 신청·승인형 | 수업형 |
|---|---|---|
| 시작 | 학생이 교수를 찾아 서비스에서 신청 | 학생의 수강 분반 정보 확인·선택 |
| 지도교수 결정 | 신청을 받은 교수의 승인 | 수강 분반에 연결된 담당 교수 |
| 별도 사전 컨택 확인 | 없음 | 해당 없음 |
| 조교의 교수 배정 | 없음 | 없음 |
| 다음 단계 이동 | 교수 승인 즉시 해당 전공만 진행 | 분반 확인 및 각 후속 단계 완료 조건에 따름 |

그 밖의 핵심 규칙은 다음과 같습니다.

- 신청과 제출은 현재 진행 단계에서 처리합니다. 필요한 앞 단계가 완료되지 않으면 후속 제출을 제한합니다.
- 수정 요청에는 사유를 남겨 학생이 무엇을 보완해야 하는지 알 수 있도록 합니다.
- 주요 신청·승인·제출·게시 등의 변경은 변경자, 시각, 내용과 함께 이력 데이터로 남습니다. 별도의 통합 감사 이력 관리 화면을 제공한다고 설명하지는 마세요.
- 한 전공의 상태 변경이 다른 전공의 진행 상태를 완료시키지 않습니다.
- 신청 제출과 교수 승인을 학과 데이터에서 별도 단계로 둘 수도 있고, 하나의 신청·승인 단계로 둘 수도 있습니다.

## 9. 현재 데모의 학과별 로드맵 예시

아래는 **공식 학과 규정이 아니라 앱 동작을 설명하기 위한 가상 예시**입니다. 실제 학과명이 쓰이지만 절차·마감·인물·연락처를 현행 공식 정보로 검증한 것은 아닙니다.

| 학과 | 방식 | 데모 단계 순서 |
|---|---|---|
| 심리학과 | 신청·승인형 | 지도교수 신청, 지도교수 승인, 연구계획서 제출, 논문 작성, 최종논문 제출·승인, 학과 제출 |
| 중어중문학과 | 신청·승인형 | 논문제출신청·개요 제출, 지도교수 신청·승인, 면담 및 작성, 졸업논문 발표회, 최종본 제출 |
| 기계공학부 | 수업형 | 기계시스템설계1 수강, 중간점검 자료 제출·교수 확인, 기계시스템설계2 수강, 포스터 발표회, 최종논문 제출·승인 |

현재 시드에서는 세 학과 모두 주전공·복수전공 논문 필수로 설정되어 있습니다. 이는 시연용 가정입니다. 면제라는 데이터 값은 시스템에서 처리할 수 있지만, 현재 시드에 사회학과 복수전공 면제 사례가 있다고 설명하면 안 됩니다.

대표 시연 학생은 심리학과와 중어중문학과를 함께 이수합니다. 별도로 기계공학부 수업형 학생, 초과학기 학생 사례가 있습니다. 학생과 교수의 이름·학번·연락처는 모두 가상입니다.

## 10. 역할 간 연결을 보여주는 대표 시나리오

1. **학과 조교가 절차를 게시:** 마감일을 수정하고 임시저장합니다. 이때 학생 화면은 바뀌지 않습니다. 게시하면 학생 로드맵과 일정이 바뀌고 알림이 생깁니다.
2. **학생이 지도 신청:** 해당 전공의 교수를 찾아 연구 방향을 작성하고 신청합니다. 신청 초안은 새로고침 후에도 유지됩니다.
3. **교수가 면담 요청:** 연구 내용을 검토하고 피드백과 가능 시간을 보냅니다. 학생이 한 시간을 선택하면 양쪽에서 확정 일정을 확인합니다.
4. **교수가 승인:** 해당 전공의 지도교수 단계가 완료되고 연구계획서 단계로 진행합니다. 다른 전공의 로드맵은 그대로 유지됩니다.
5. **자료 제출과 보완:** 학생이 연구계획서와 최종논문을 단계에 맞춰 제출합니다. 교수의 수정 요청을 받으면 보완하여 새 버전으로 재제출하고, 승인 후 다음 단계로 진행합니다.

이 시나리오는 역할별 기능 목록을 단순 나열하는 대신, 각 역할의 행동이 누구의 화면과 상태를 바꾸는지 설명하는 데 사용할 수 있습니다.

## 11. 가치 제안과 기대 효과

| 사용자 | 현재 겪는 과업 | 서비스가 지원하는 변화 |
|---|---|---|
| 학생 | 여러 공지를 찾아 개인별 절차로 다시 정리 | 전공별 단계와 다음 행동, 제출 정보 및 통합 일정 확인 |
| 교수 | 신청 내용과 자료, 검토 결과, 면담 일정을 확인 | 신청·제출물과 피드백·면담을 하나의 업무 흐름에서 처리 |
| 학과 조교 | 학과 절차 공지와 학생별 진행 상태 관리 | 절차를 편집·게시하고 대상별 공지 및 진행 현황 조회 |

차별적으로 설명할 지점은 **학과별 절차의 차이를 데이터에 반영한다는 점**, **학생의 전공 조합에 맞춰 정보를 보여준다는 점**, **일정 안내와 실제 신청·검토 상태를 연결한다는 점**입니다.

반복 검색과 문의를 줄이고 마감 누락을 예방하는 것을 목표로 합니다. 아직 실제 사용자 대상으로 시간 절감이나 누락 감소 효과를 측정하지 않았으므로 효과가 입증되었다고 쓰지 마세요.

## 12. 기술 및 데모 범위

- Next.js App Router, TypeScript, Tailwind CSS를 사용한 웹앱입니다.
- Zustand persist와 브라우저 localStorage로 데모 데이터를 저장합니다.
- 첫 화면에서 역할을 선택하고, 상단에서 학생/교수/학과 조교와 가상 사용자를 전환합니다. 로그인은 없습니다.
- 데모 초기화로 시드 상태로 되돌릴 수 있습니다.
- 같은 브라우저에서 역할을 바꾸며 상호 연결된 동작을 시연합니다. 여러 컴퓨터·계정 간 실시간 서버 동기화는 없습니다.
- 파일은 서버가 아니라 브라우저에 저장합니다. PDF/DOCX를 지원하며 파일당 512KB, 전체 저장량도 제한합니다.
- PDF 미리보기와 PDF/DOCX 다운로드를 제공하고 DOCX는 외부 문서 편집기로 엽니다.
- 모바일 375px와 데스크톱을 고려한 반응형 화면입니다.
- 최신 UI의 주요 강조색은 짙은 파란색(#0F0F70)이며, 전공별 색은 일정 구분 등에 사용합니다. 학교 공식 서비스로 표현하지 마세요.

구현되지 않은 범위:

- 실제 인증, 학사 시스템·DB·외부 API 연동
- 실제 이메일·SMS 발송
- 학과 홈페이지 자동 수집, 공지 PDF의 AI 분석·구조화
- 공식 문서 질의응답 챗봇
- 서버 파일 업로드, 보안 검사, 영구 문서 보관
- 학과 조교의 지도교수 배정, 정원 수정, 교수 승인 후 재확정
- 모든 전공의 최우선 과업 자동 선정, 같은 주 마감 충돌 자동 경고
- 실제 사용자 조사로 확인한 성과 수치

프로젝트의 핵심은 현재 AI 기능이 아니라 **학과별 절차 데이터와 역할별 업무 연결**입니다. AI 서비스를 구현한 것처럼 소개하지 마세요.

## 13. 기존 자료를 사용할 때 주의할 점

- 초기 기획 문서에는 학생 사전 컨택 확인, 행정실 확정 검토, 행정실의 수업형 교수 배정 등이 있지만 최신 구현에서는 제거되었습니다.
- 최신 구현은 교수 승인 즉시 진행, 수강 분반에서 지도교수 확인, 학과 조교의 절차·공지 관리입니다.
- 초기 학과 예시의 사회학과는 현재 시드에 없습니다. 최신 시드는 심리학과·중어중문학과·기계공학부입니다.
- 앞서 제작한 PPTX의 기능 화면 이미지는 최신 파란색 테마와 6개 학생 업무 탭 적용 전 캡처입니다. 현재 화면이라고 그대로 재사용하지 말고 필요하면 최신 캡처를 요청해 주세요.
- 실제 공식 공지 사례와 앱의 가상 학과 데이터를 혼동하지 마세요. 공식 공지는 문제 배경의 근거이며, 앱에 그 공지 전체가 연동되어 있다는 뜻이 아닙니다.
